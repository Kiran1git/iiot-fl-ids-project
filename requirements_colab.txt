# flwr==1.8.0 declares, verbatim from its PyPI metadata:
#       numpy   <2.0.0, >=1.21.0
#       protobuf <5.0.0, >=4.25.2

#       protobuf >=5.28.0        <-- UNSATISFIABLE against flwr 1.8.0
#       numpy    >=1.26.0
#       keras    >=3.10.0
# There is NO version of protobuf that satisfies both "<5.0.0" and ">=5.28.0".
# Therefore TF 2.20 + flwr 1.8.0 is a mathematically impossible resolution, and
# it is the exact source of the protobuf/TensorFlow conflict being reported.

# it either), TensorFlow is the variable that must move. TF 2.19.1 is the newest
# TensorFlow whose protobuf floor is still 3.20.3 with a <6.0.0dev ceiling —
# i.e. the newest TF that can coexist with protobuf 4.25.x.
#
# CONFLICT RESOLUTION SUMMARY (why each conflict disappears)
#   protobuf : TF 2.20 needs >=5.28 / flwr needs <5.0  ->  TF pinned to 2.19.1,
#              whose range is >=3.20.3,<6.0.0dev; 4.25.8 satisfies everything.
#   numpy    : Colab ships 2.x; flwr caps at <2.0      ->  numpy 1.26.4 pinned,
#              which is also TF 2.19's floor for py3.12 and shap/numba-safe.
#   keras    : TF >=2.16 defaults to Keras 3; shap's GradientExplainer needs
#              Keras 2                                 ->  tf-keras 2.19.0 +
#              TF_USE_LEGACY_KERAS=1.
#   ray      : the SDS pin 2.6.3 has no cp312 wheel    ->  2.31.0 (first cp312
#              wheel line), and its protobuf floor (>=3.15.3) is compatible.
#
# USAGE (exact order — see COLAB SETUP at the bottom of this file):

# --- Core DL runtime ---------------------------------------------------------
# tensorflow 2.19.1 — chosen, not defaulted to.
#   * cp312 manylinux_2_17_x86_64 wheel exists (verified on PyPI), so it installs
#     on Colab's Python 3.12.
#   * protobuf range is ">=3.20.3,<6.0.0dev" — the last TF line that still
#     accepts protobuf 4.x. TF 2.20.0 raised the floor to ">=5.28.0" and TF
#     2.21.0 to ">=6.31.1"; both are hard-incompatible with flwr 1.8.0's
#     "protobuf<5.0.0". This single constraint is why 2.19.1 and not 2.20.
#   * numpy range is ">=1.26.0,<2.2.0", which contains 1.26.4 — so TF and flwr's
#     "numpy<2.0.0" can be satisfied simultaneously. TF 2.20 does NOT declare a
#     numpy upper bound but is built and tested against numpy 2.x, so forcing it
#     down to 1.26.4 is unsupported; 2.19.x is.
#   * GPU: the plain `tensorflow` wheel from 2.19 onward bundles the CUDA 12
#     stack it needs on Linux, so tf.config.list_physical_devices("GPU") sees
#     the Tesla T4 without [and-cuda] and without touching Colab's drivers.
#     (T4 is SM 7.5; TF 2.19 ships SM 7.5 kernels.)
#   * Keras/SavedModel semantics: 2.19 still supports `model.save("*.h5")` and
#     `load_model("*.h5")`, which src/federated/server_app.py,
#     src/centralized/train_baseline.py, compare_fl_vs_centralized.py and
#     dashboard/app.py all depend on. No code change is required.
tensorflow==2.19.1

# tf-keras 2.19.0 — KERAS 2 COMPATIBILITY (load-bearing; both this pin and the
# TF_USE_LEGACY_KERAS env var are required, neither works alone).
#   * Version is forced: tf-keras 2.19.0 declares "tensorflow>=2.19,<2.20", so it
#     is the ONLY tf-keras release that pairs with the TF pin above. (2.20.x
#     would drag TF 2.20 back in and re-create the protobuf conflict.)
#   * Why it is needed at all: TF >=2.16 makes Keras 3 the default `tf.keras`.
#     shap 0.4x's GradientExplainer walks Keras 2 / TF-graph internals
#     (tf.gradients over the model's op graph) and breaks against Keras 3.
#     src/explainability/shap_utils.py calls shap.GradientExplainer directly, so
#     this is a functional requirement, not a nicety.
#   * It also restores Keras-2 .h5 saving semantics for
#     `global_model.save("federated_global_model.h5")`.
tf-keras==2.19.0

# keras — pinned to satisfy TF 2.19's "keras>=3.5.0" without letting pip pull a
# Keras 3.11+/3.12+ build. Keras 3 is still installed (TF imports it
# unconditionally at load time) but is bypassed at runtime by
# TF_USE_LEGACY_KERAS=1. The <3.11 ceiling keeps Keras's own numpy expectations
# inside the numpy 1.26.4 world.
keras>=3.5.0,<3.11.0

# =============================================================================
# WHY NOT TENSORFLOW 2.20 (the version Colab already has working on the T4)
# =============================================================================
# Keeping 2.20 was evaluated first and rejected on hard metadata grounds:
#
#   tensorflow 2.20.0 -> protobuf >=5.28.0
#   flwr       1.8.0  -> protobuf <5.0.0
#
# The intersection is empty. pip either aborts with a ResolutionImpossible or —
# if either package is installed with --no-deps — silently produces a broken
# environment where `import flwr` raises inside its generated *_pb2.py modules
# ("Descriptors cannot be created directly" / builder API mismatch).
#
# Three escape routes were considered and rejected:
#   1. Upgrade flwr past 1.8.0 — does not help: every flwr up to 1.13.1 still
#      declares protobuf<5.0.0, and 1.13+ additionally removes start_simulation,
#      which SDS Sections 5 and 14.6 forbid replacing.
#   2. Install with PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python and mismatched
#      protobuf — works by accident at best; the pure-Python fallback is 10-50x
#      slower on the message serialisation that Flower does every round, and it
#      is still an unsupported descriptor-pool combination.
#   3. --no-deps installs to hide the conflict — leaves the environment
#      unverifiable, which is the situation this file exists to end.
#
# Downgrading TF to 2.19.1 is the only route that leaves BOTH packages inside
# their declared metadata, and it costs nothing functionally: 2.19 has the same
# cp312 wheel, the same bundled CUDA 12 stack, the same T4 support, and the same
# .h5 save/load behaviour the project relies on.
#
#
# =============================================================================
# FLOWER API: NO CODE CHANGES REQUIRED
# =============================================================================
# flwr is held at the SDS-pinned 1.8.0, so every Flower call site is untouched:
#   * src/federated/server_app.py — flwr.simulation.start_simulation(
#         client_fn=..., num_clients=..., config=flwr.server.ServerConfig(...),
#         strategy=..., client_resources=..., ray_init_args=...)
#   * src/federated/client_app.py — FLClient(NumPyClient),
#         client_fn(cid) -> client.to_client()
#   * SavingFedAvg(FedAvg), weighted_average_fit / weighted_average_eval,
#         flwr.common.parameters_to_ndarrays
#   * tests/test_federated_loop.py — drives the same start_simulation API
#
# Had flwr been upgraded to >=1.13 (where start_simulation is removed), these
# changes would have been forced — all of them SDS violations:
#   1. server_app.py: start_simulation(...) -> flwr.simulation.run_simulation(
#        server_app=ServerApp(...), client_app=ClientApp(...),
#        num_supernodes=...). Violates SDS Section 5 and Section 14.6.
#   2. client_app.py: client_fn(cid: str) -> client_fn(context: Context), with
#        the client ID read from context.node_config["partition-id"]. The
#        functools.partial binding of client_shards/test_data/config in
#        run_federated_simulation would have to be reworked.
#   3. ray_init_args / client_resources -> backend_config={"client_resources":
#        {...}, "init_args": {...}}, so build_ray_init_args() and
#        build_client_resources() would both need rewriting.
#   4. History's losses_distributed / metrics_distributed / losses_centralized /
#        metrics_centralized accessors would need re-verification.
# None of the above is implemented, because flwr stays at 1.8.0.
#
#

# =============================================================================
# KNOWN RISKS UNDER THIS FILE
# =============================================================================
#
# 1. Keras 3 leakage. If TF_USE_LEGACY_KERAS=1 is not set before the first
#    `import tensorflow`, tf.keras resolves to Keras 3 and
#    shap.GradientExplainer fails inside generate_shap_explanations(). The
#    assert in Cell 2 catches this immediately rather than 40 minutes into a run.
#
# 2. Colab's own preinstalled packages. Downgrading numpy to 1.26.4 and protobuf
#    to 4.25.8 can make unrelated Colab packages (bigframes, some google-cloud
#    clients) report incompatibility under `pip check`. None of them are imported
#    by this project — only warnings about packages outside this file are safe to
#    ignore. Any warning naming tensorflow, flwr, ray, shap or numpy is not.
#
# 3. .h5 model portability. Models written by the frozen TF 2.15.1 stack load
#    under TF 2.19 + tf-keras, but models written here should not be assumed
#    loadable by the 2.15.1 stack. Do not mix artifacts across the two
#    environments — regenerate within whichever environment you are using.
#
# 4. Numerical non-identity. Different TF/CUDA builds change floating-point
#    reduction order, and GPU execution is non-deterministic in ways CPU runs are
#    not, so results from this file will not be bit-identical to the frozen stack
#    even at the same seed. SDS Section 23's reproducibility criteria are defined
#    against requirements.txt, not this file.
#
# 5. T4 memory. The T4 has 16 GB. Four concurrent Ray client actors each holding
#    a TensorFlow runtime can exhaust it. If you hit OOM, set
#    `federated.client_num_cpus: 2` in configs/config.yaml — build_client_resources()
#    already serialises the actors from that key, with no change to the FedAvg
#    result (clients within a round are independent).
