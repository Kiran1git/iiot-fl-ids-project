# --- Core DL runtime ---------------------------------------------------------
# 2.17.x is the newest TF line that still ships an official cp312 wheel while
# remaining on the TF 2.x graph/SavedModel semantics this project's .h5 models
# and build_cnn_gru rely on. Chosen over 2.19/2.20 to stay as close to the
# pinned 2.15.1 behaviour as the platform allows.
tensorflow==2.17.1

# KERAS 2 COMPATIBILITY (load-bearing — do not remove either line)
# TF >= 2.16 makes Keras 3 the default `tf.keras`. shap==0.4x's
# GradientExplainer walks Keras 2 internals and breaks against Keras 3.
# tf-keras restores the Keras 2 implementation, and the environment variable
# TF_USE_LEGACY_KERAS=1 makes `tf.keras` resolve to it. BOTH are required:
# installing tf-keras without setting the variable changes nothing.
tf-keras==2.17.0

# --- Federated learning ------------------------------------------------------
# HELD AT THE SDS PIN. flwr 1.8.0's start_simulation(client_fn=..., ...) API is
# what src/federated/server_app.py calls, and it is Python 3.12-compatible
# (pure Python, no compiled extension). Do NOT bump this: start_simulation was
# removed in Flower 1.13+, which would force the SDS-forbidden app-based API and
# a rewrite of both server_app.py and client_app.py.
flwr[simulation]==1.8.0

# Ray backs flwr[simulation]'s VirtualClientEngine. ray==2.6.3 (the SDS pin) has
# no cp312 wheel, so it is raised to the lowest release that does. 2.31.0 is
# still within the 2.x actor/resource API surface that flwr 1.8.0's
# start_simulation drives via ray_init_args and client_resources, so
# build_ray_init_args() and build_client_resources() in server_app.py keep
# working unmodified.
ray==2.31.0

# --- Numerics ----------------------------------------------------------------
# NumPy 2.x is a hard conflict here: tensorflow 2.17 and shap 0.4x are both
# built against the NumPy 1.x C ABI, and ray 2.31 likewise. The <2.0 ceiling is
# the single most important constraint in this file — relaxing it produces
# "_ARRAY_API not found" / "compiled using NumPy 1.x cannot be run in NumPy 2.x"
# at import time. Colab preinstalls NumPy 2.x, which is exactly why the runtime
# restart after install is mandatory.
numpy>=1.26,<2.0

# protobuf: the tightest simultaneous constraint in the whole set. TF 2.17
# requires >=3.20.3,<5.0, ray 2.31 requires >=3.15.3, and flwr 1.8.0 requires
# >=3.19,<5.0 (via grpcio-tools). 4.25.x is the only line satisfying all three
# with cp312 wheels. Colab preinstalls protobuf 5.x for its own packages, so
# this WILL be downgraded on install — that downgrade is intended, and is the
# second reason the runtime restart is mandatory.
protobuf>=4.25.3,<5.0

# --- Explainability ----------------------------------------------------------
# Raised from the SDS's 0.44.1 (no cp312 wheel) to the lowest release providing
# one. 0.46.0 keeps the GradientExplainer API that
# src/explainability/shap_utils.py calls — explainer.shap_values(...) and
# shap.summary_plot(...) are unchanged, so the mandatory four-step squeeze in
# generate_shap_explanations() still applies exactly as written.
shap==0.46.0

# --- Classical ML / data -----------------------------------------------------
# scikit-learn raised from the SDS's <1.5 ceiling for cp312 wheel availability.
# Only LabelEncoder, train_test_split, compute_class_weight and the sklearn.metrics
# functions are used; all are API-stable across this range.
scikit-learn>=1.5,<1.7
pandas>=2.2,<2.3
pyarrow>=14.0            # read_processed() reads .parquet; not implied by pandas

# --- Visualization / app -----------------------------------------------------
matplotlib>=3.8,<3.10
streamlit>=1.37,<1.40

# --- Config / test -----------------------------------------------------------
pyyaml>=6.0
pytest>=7.4


# =============================================================================
# FLOWER API: NO CODE CHANGES REQUIRED
# =============================================================================
#
# You asked me to explain any code changes needed if newer Flower APIs are
# required. The answer is that none are needed, and this is deliberate.
#
# flwr is held at the SDS-pinned 1.8.0 above, so every Flower call site in the
# project is untouched:
#
#   * src/federated/server_app.py — flwr.simulation.start_simulation(
#         client_fn=..., num_clients=..., config=flwr.server.ServerConfig(...),
#         strategy=..., client_resources=..., ray_init_args=...)
#   * src/federated/client_app.py — FLClient(NumPyClient) and
#         client_fn(cid) -> client.to_client()
#   * SavingFedAvg(FedAvg), weighted_average_fit / weighted_average_eval,
#         flwr.common.parameters_to_ndarrays
#   * tests/test_federated_loop.py — drives the same start_simulation API
#
# For the record, had Flower been upgraded to >= 1.13 (where start_simulation is
# removed), these changes would have been forced — all of them SDS violations:
#
#   1. server_app.py: start_simulation(...) -> flwr.simulation.run_simulation(
#        server_app=ServerApp(...), client_app=ClientApp(...),
#        num_supernodes=...). Directly violates SDS Section 5 and Section 14.6.
#   2. client_app.py: client_fn's signature changes from client_fn(cid: str) to
#        client_fn(context: Context), with the client ID read from
#        context.node_config["partition-id"] instead of the cid argument. The
#        functools.partial binding of client_shards/test_data/config in
#        run_federated_simulation would have to be reworked into a Context-based
#        mechanism.
#   3. ray_init_args / client_resources: replaced by backend_config=
#        {"client_resources": {...}, "init_args": {...}}, so
#        build_ray_init_args() and build_client_resources() would both need
#        rewriting.
#   4. The History object's losses_distributed / metrics_distributed /
#        losses_centralized / metrics_centralized accessors that
#        run_federated_simulation reads to build federated_history.csv would
#        need re-verification against the new API.
#
# None of the above is implemented, because flwr stays at 1.8.0.
#
#

# KNOWN RISKS UNDER THIS FILE
# =============================================================================
#
# 1. Keras 3 leakage. If TF_USE_LEGACY_KERAS=1 is not set before the first
#    `import tensorflow`, tf.keras resolves to Keras 3 and
#    shap.GradientExplainer fails inside generate_shap_explanations(). The
#    assert in Cell 2 exists to catch this immediately rather than 40 minutes
#    into a run.
#
# 2. .h5 model portability. Models written by the frozen TF 2.15.1 stack load
#    under TF 2.17 + tf-keras, but models written under this file should not be
#    assumed loadable by the 2.15.1 stack. Do not mix artifacts across the two
#    environments — regenerate within whichever environment you are using.
#
# 3. Numerical non-identity. Different TF/CUDA builds change floating-point
#    reduction order, so results from this file will not be bit-identical to the
#    frozen stack even at the same seed. SDS Section 23's reproducibility
#    criteria are defined against requirements.txt, not this file.
#

#    been executed on a Colab runtime from this workspace — validate with Cell 3
